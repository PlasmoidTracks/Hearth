## Part B — Architecture assessment

### Tool system
- **Current shape:** an abstract `Tool` base (`tools/base.py:70-110`) with `enable_key` / `gated`, plus a hand-maintained singleton list `_ALL_TOOLS` and a derived `TOOLS_BY_NAME`. Gating resolves cleanly in one place (`tools/__init__.py:approval_mode`), and the output guard is genuinely well-placed — `orchestrator._run_tool` → `_guard_result` covers every tool, present and future, without tool cooperation.
- **Where the next feature lands:** adding one tool touches `tools/<new>.py`, `tools/__init__.py` (import + list), `runtime_settings.py` (`_TOOL_LABELS`), and — if it needs approval UI prose — `_approval()`. **3 shared files, 2 of them registries.**
- **Seam:** partial. The real seam is missing at registration; the guard and context seams are good.
- **Highest-value refactor:** a `@register` decorator that appends to `_ALL_TOOLS` as a side effect and carries its own label — this deletes one of the two shared files entirely and makes `_TOOL_LABELS` derived rather than hand-synced. Do not touch the guard; it's the best-designed seam in the codebase.

### LLM provider abstraction
- **Current shape:** `Provider.stream(messages, tools, params) -> AsyncIterator[StreamEvent]` (`llm/base.py:67-77`) is a clean, honest interface, and `StreamEvent` covers the eight cases Hearth actually cares about.
- **Where the next feature lands:** an OpenAI-compatible or Ollama backend means new `llm/<x>.py`, plus `manager.get_provider()` (`manager.py:36-45`), plus `model.backend`'s hardcoded `choices=["stub","llama-server"]` (`runtime_settings.py:45`), plus the provider-name string check in `_agent_loop:1230` (`getattr(provider,"name","")=="llama-server"` for log polling). **4 places, one of them a capability sniff by string equality.**
- **Seam:** the interface *is* the seam and it's sound; what's missing is a registry and a capability-descriptor object (does this provider expose live progress? measured usage?).
- **Highest-value refactor:** `PROVIDERS: dict[str, type[Provider]]` + `Provider.capabilities()` — replacing both the if-chain and the name-string sniff. Cheap, and the single biggest "hard to build on" complaint in the LLM layer.

### Settings / config
- **Current shape:** genuinely good design — `config.py` (boot, env, read-only) vs `runtime_settings.py` (DB-backed, admin-editable, typed, with help text and safe ranges). The `_coerce` fallback-to-default behaviour is defensive in the right direction.
- **Where the next feature lands:** nowhere — this is the module things *should* go into, and they don't. Hardcoded policies that bypass it: `MAX_UPLOAD_BYTES` (routes_chat:49), workspace listing 80 (orchestrator:91), `list_tree` default 500 (workspaces:76), `fs_search` 400/60, `zip_pack` 200 files / 64 MiB, `pdf_read` 6 pages, `view_video` 16 frames / 120 s audio window, `UI_PREVIEW_MAX_CHARS` 4 000. **Eight policy values live outside the settings system that exists to govern them.**
- **Seam:** exists and is trivially extensible (add a `SettingSpec`).
- **Highest-value refactor:** no new seam needed — just move the eight constants in, starting with `uploads.max_bytes` and `workspace.listing_entries`. The pattern for doing this is already in the file.

### Artifact & workspace layer
- **Current shape:** clean separation of concerns — jail resolution/canonicalisation in `workspaces.py`, durable records in `artifacts.py`, ownership-scoped download in routes. `_norm_rel` dedupe, monotonic `_next_seq`, and the FK-drop migration all show real thought about failure modes. Encryption-at-rest is correctly encapsulated (`_read_blob`/`_write_blob`/`seal_bytes`) so no route ever handles crypto — the media tools explicitly pass *bytes* to external renderers for this reason.
- **Where the next feature lands:** versioning or content-addressing would land naturally in `artifacts.py`, but the upload path bypasses it today (finding #2) because `record(new_row=True)` records a path that was already overwritten.
- **Seam:** yes, and a good one — **except** that `record()` is called *after* the write, so it can never detect "this replaced different bytes". That ordering is the structural cause of #2.
- **Highest-value refactor:** give `artifacts.record()` a pre-write hook (`expect_new: bool`) so collision detection happens before truncation, not after.

### Prompt assembly
- **Current shape:** `prompt.assemble(system_doc, protocol_doc)` composes persona + protocol + WORKSPACE_PREAMBLE; `build_messages` then appends `_workspace_context`, `_project_context`, `_captioner_hint`. The conditional-capability discipline is excellent — `_captioner_hint` refuses to claim audio when the captioner is off, and `_vision_state` checks the *running* server rather than Admin's config.
- **Where the next feature lands:** any new prompt section means a new function in `orchestrator.py` (not `prompt.py`) plus a call site in `build_messages`, because the context-producing functions drifted into the orchestrator.
- **Seam:** conceptually present, physically misplaced. **This is also where the codebase's worst bug lives (finding #1): prose asserting "shows every file" while the code caps at 80.**
- **Highest-value refactor:** move `_workspace_context`/`_project_context`/`_captioner_hint` into `prompt.py` as a `ContextSource` list, so prompt composition is testable without importing the agent loop — and so the "every file" claim can be checked against the actual cap in one module.

### Media handling
- **Current shape:** strong layering — `media_render.py` does subprocess/backend detection (pymupdf → pdftoppm → gs) and raises typed `MediaError`; `media_tools.py` decides policy; images travel as jail-relative paths in `ToolResult.images`, materialised into a transient user-role multimodal message by `build_messages`. The "paths not base64 in the DB" choice is right. Failure handling is unusually honest: `_store_images` drops a failed frame but the result *names* how many couldn't be saved (`media_tools.py:253-256`).
- **Where the next feature lands:** a new modality (audio transcription display, 3D) touches `media_render.py`, `media_tools.py`, `chat.js` renderers, and `orchestrator._image_parts`. **4 files.**
- **Seam:** yes for rendering (typed errors, backend fallback), no for delivery — the multimodal shape is hardcoded to `image_url` in three places (`_image_parts`, `_attachment_content`, `_strip_image_parts`).
- **Highest-value refactor:** one `to_multimodal_part(kind, path)` function; every image-shape decision currently has to be repeated in the strip/recover logic.

### The agent loop
- **Current shape:** `_agent_loop` (1 173–1 523) drives model round-trips, steering delivery, repeat suppression, `_DONE_NOTE` injection, gated/auto partitioning, usage merge and vision recovery. `_stream_checked` (849–1 120) is a separate, extremely carefully-commented race between provider read / idle timeout / abort / log poll.
- **Where the next feature lands:** anything touching turn sequencing — parallel tool execution, sub-agents, mid-turn compaction — goes into `_agent_loop`, which has no extension points, only branches. Compounding this: `_resume_pending` starts a **fresh** `_agent_loop` with `round_offset=1000`, so loop state (`calls_done`) does not survive a gated resume — meaning repeat-suppression silently resets across an approval boundary.
- **Seam:** the steering seam is real and well-designed (drain at the between-rounds point, documented as "the whole design" in `steering.py`). The output-guard seam is real. There is no loop-policy seam.
- **Highest-value refactor:** extract a `TurnState` object carrying `calls_done`, `turn_usage`, `round_id`, `_strip_images_for` — it makes the offset-1000 hack unnecessary and turns the loop testable without a provider.

### B2 — Unreachable duplicated code
`hearth/orchestrator.py:804-846`: 43 lines containing a second copy of `_progress_event`'s body sit after `_merge_progress`'s top-level `return`. Verified by AST (`stmt[4] Return 802-802`, then `Expr 804-821 / Assign 822 / If 823-845 / Return 846`). It is dead, and it duplicates ETA logic that now lives in `_merge_progress` — a future fix applied to the wrong copy will silently do nothing.

### B3 — Prompt asserts something the code does not do
`prompt.py` tells the model *"The workspace listing in this prompt shows every file"* while `orchestrator.py:91` caps it at 80. This is not merely a doc mismatch, it's an active misinstruction: a model told the listing is complete has no reason to call `fs_list`, so the cap becomes invisible even to the agent. Verified by running both constants side by side (see finding #1).

### B4 — Client/server link-count disagreement
`web.max_links` defaults to 30 and its own help text says links are *"shown as source links"*, but `chat.js:189` renders `web.links.slice(0,6)`. Raising the setting changes model input only. *Inferred from reading both sides* — not exercised in a browser.

### B5 — Silent truncation in a success message
`fs_tools.py:375` iterates `paths[:200]`, then reports success as `f"packed {len(resolved)} files into {zname}"`. A caller passing 250 paths gets a zip of 200 and a truthful-looking count. *Inferred from reading*; no test covers >200 paths.

### B6 — `_progress_event` / `_merge_progress` overlap (unresolved)
Both compute `eta_s`/`eta`, and `_poll_log` calls `_merge_progress` then `_progress_event` per event (`orchestrator.py:1090-1093`). Whether the second clobbers the first's baseline-derived ETA is a behaviour claim I could not verify without running a live llama-server. Flagged as unverified rather than asserted.
